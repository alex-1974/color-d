# R0.13 — Numerical tolerance and reference policy

**Status:** CONTRACT
**GitHub:** #9 — R0.13 — Define numerical tolerance and reference policy

R0.13 defines the numerical comparison and reference strategy needed before
validated R0 research is promoted into production tests and API.

This block does not begin by choosing an epsilon.

Its central question is:

> Which numerical comparison rule is correct for each mathematical property,
> operation class and reference source?

No public API is established by this experiment.

---

# 1. Research boundary

R0.13 studies numerical comparison policy.

It does not reopen the mathematical semantics already established by R0.1–R0.12.

The block distinguishes at least:

```text
mathematical operation
        ↓
property being asserted
        ↓
comparison class
        ↓
reference source
        ↓
scalar-specific acceptance criterion
```

The comparison criterion belongs to the property being tested.

It must not be selected merely because a test otherwise fails.

---

# 2. Existing evidence

Earlier R0 blocks already provide several distinct comparison cases.

Examples include:

```text
exact component preservation
exact structural equality
exact flags / iteration metadata
exact analytical identities
reference-vector comparison
round-trip comparison
near-achromatic policy
strict gamut membership
epsilon-aware numerical boundary checks
runtime / CTFE comparison
compiler-cross comparison
```

Those are not assumed to share one numerical tolerance.

R0.13 consolidates and validates the policy implied by that evidence.

---

# 3. Central hypothesis

The primary hypothesis is:

> color-d requires a taxonomy of comparison contracts rather than one global
> floating-point epsilon.

The expected comparison classes are:

```text
A. exact equality

B. classification / domain predicates

C. independent reference-value comparison

D. derived / round-trip numerical comparison

E. cross-execution comparison
   runtime ↔ CTFE
   compiler ↔ compiler

F. policy-driven approximate classification
```

R0.13 must verify whether this taxonomy is sufficient and whether any classes
need refinement.

---

# 4. Non-negotiable rule: exact properties remain exact

An approximation tolerance must not replace an exact semantic property.

Candidate exact properties include:

```text
copied components
stored raw hue
explicitly preserved endpoints
cardinality / structure
status flags
success flags
iteration counts
identity cases defined exactly
same-value distance == 0 where algebraically exact
same-color contrast == 1 where algebraically exact
```

Each property must still be checked individually.

R0.13 must not infer exactness merely from the examples above.

Likewise, an implementation must not be accepted as correct merely because its
error falls within a broad numerical tolerance if the intended property is
exact.

---

# 5. Classification is not ordinary approximate equality

Predicates such as:

```text
in gamut
out of gamut
achromatic
near-achromatic
inside domain
outside domain
```

have semantic boundaries.

R0.13 distinguishes:

```text
strict mathematical classification
```

from:

```text
policy-driven numerical proximity to a boundary
```

An epsilon-aware classification helper, where justified, must not redefine the
strict mathematical predicate.

For example:

```text
strict inGamut(color)
```

and:

```text
numericallyNearGamutBoundary(color, policy)
```

represent different questions.

The exact API spelling is not decided here.

---

# 6. Reference hierarchy

Reference values must carry provenance.

Candidate reference classes are:

```text
1. normative standards / specification examples
2. independently derived analytical values
3. independent higher-precision implementations
4. independently implemented algorithmic reference paths
5. previously validated color-d research fixtures
6. self-round-trip values
```

These classes are not equally authoritative.

R0.13 must determine which are appropriate for:

```text
semantic conformance
regression testing
implementation comparison
numerical characterization
```

A production regression test should prefer an independent reference over a
value generated by the same implementation under test whenever practical.

---

# 7. Scalar policy

`float` and `double` must be characterized separately.

R0.13 must not assume:

```text
float tolerance = scaled double tolerance
```

without evidence.

For each relevant operation class record:

```text
absolute error
relative error where meaningful
ULP distance where meaningful
reference magnitude
input magnitude / domain
runtime versus CTFE behavior
compiler/build configuration
```

A scalar-specific rule may be justified.

A scalar-specific magic constant is not justified merely because it makes the
current samples pass.

---

# 8. Absolute, relative and ULP comparisons

R0.13 considers three common numerical comparison families.

## 8.1 Absolute tolerance

Potentially useful near zero or where the mathematical scale is naturally
bounded.

Conceptually:

```text
abs(actual - expected) <= absTol
```

It is inappropriate as a universal rule across arbitrary magnitudes.

## 8.2 Relative tolerance

Potentially useful when error should scale with the reference magnitude.

Conceptually:

```text
abs(actual - expected) <= relTol * scale
```

The correct scale function must be justified.

Near zero requires separate treatment.

## 8.3 ULP-oriented comparison

Potentially useful for detecting low-order representational differences between
nearby finite floating-point values.

ULP comparison is not automatically a semantic error metric.

R0.13 must determine whether ULP distance provides useful regression evidence
for any operation class.

It must not impose a portable ULP guarantee without evidence.

---

# 9. Combined comparisons

A combined rule such as:

```text
abs(error) <= absTol
or
abs(error) <= relTol * scale
```

may be appropriate for some operation classes.

R0.13 must not assume this form universally.

If such a rule is adopted, its:

```text
absolute floor
relative term
scale definition
NaN behavior
infinity behavior
signed-zero behavior
```

must be explicit.

---

# 10. Special floating-point values

R0.13 must keep semantic handling of:

```text
NaN
+infinity
-infinity
+0
-0
```

separate from ordinary finite approximate comparison.

A generic approximate comparator must not silently equate:

```text
NaN with NaN
finite with infinity
opposite infinities
```

unless an explicitly documented property requires such behavior.

Signed-zero treatment must follow the semantics of the property under test.

---

# 11. Operation classes in scope

R0.13 covers at least the operation classes required by GitHub #9.

## Transfer functions

```text
encoded sRGB ↔ linear sRGB
```

Questions:

- normative reference values;
- branch-boundary behavior;
- float/double error;
- forward/inverse round trip;
- runtime/CTFE agreement.

## Matrix transforms

```text
linear sRGB ↔ XYZ D65
```

Questions:

- independent matrix references;
- ordinary and extended-range inputs;
- float/double forward error;
- round-trip error;
- accumulation effects.

## Oklab transforms

```text
XYZ D65 ↔ Oklab
```

Questions:

- independent reference vectors;
- cube-root behavior;
- extended finite values;
- float/double round trips;
- runtime/CTFE differences.

## OKLCH / hue operations

Questions:

- exact achromatic semantics;
- non-achromatic conversion error;
- trigonometric error;
- hue wrap and exact tie cases;
- round-trip behavior;
- near-achromatic policy remains explicit.

## Alpha / compositing

Questions:

- exact identity/absorbing cases where algebraically guaranteed;
- source-over reference vectors;
- premultiply/unpremultiply round trips where defined;
- associativity as approximate numerical behavior rather than an exact
  floating-point requirement.

## Interpolation

Questions:

- exact endpoint requirements;
- exact tie-policy decisions;
- interior arithmetic;
- hue-path calculations;
- whether numerical tolerance is needed only for derived interior values.

## Gamut classification

Questions:

- strict membership semantics;
- boundary behavior;
- numerical proximity helpers;
- whether tolerance belongs in testing, explicit policy, or both.

## Gamut mapping

Questions:

- reference-algorithm comparison;
- stable metadata/status;
- mapped-color numerical comparison;
- convergence and stopping criteria;
- runtime/CTFE behavior.

## WCAG luminance / contrast

Questions:

- normative reference path;
- exact identity cases;
- transfer-function inherited error;
- contrast reference comparisons.

## deltaEOK

Questions:

- exact zero-distance identity;
- analytical simple cases;
- higher-precision reference route;
- norm implementation comparison;
- float/double numerical behavior.

## Palette / CTFE integration

Questions:

- raw values that should remain exact;
- mapped/encoded runtime-versus-CTFE differences;
- cross-compiler behavior;
- whether observed differences remain semantically insignificant under the
  operation-specific comparison rules established above.

# 12. R0.12 handoff

R0.12-C established an important comparison boundary.

For its tested palette pipeline:

```text
raw runtime values
    == CTFE raw values exactly

Ray Trace success / iteration metadata
    == CTFE metadata exactly
```

but:

```text
mapped floating-point components
encoded floating-point components
```

were not bit-for-bit equal between runtime and CTFE.

Observed maximum absolute component differences in that experiment were
approximately:

```text
float:
    mapped   2.9206276e-06
    encoded  1.5497208e-06

double:
    mapped   1.332e-15
    encoded  8.882e-16
```

These values are observations.

They are not R0.13 tolerance constants.

R0.13 must reproduce and contextualize the relevant behavior across the
supported compiler matrix before deriving any policy from it.

# 13. Compiler matrix

The supported correctness baseline remains:

```text
DMD 2.111.0
LDC 1.41.0
```

R0.13 must validate numerical policy from the baseline upward using the
controlled compiler installations already established by the project.

The initial comparison matrix is:

```text
DMD 2.111.0
DMD 2.112.0
DMD 2.112.1
DMD 2.113.0

LDC 1.41.0
LDC 1.42.0
LDC 1.43.0
```

Debug and Release must both be used where optimization can alter numerical
behavior.

The experiment may reduce the full matrix for exploratory work, but final
claims affecting baseline support require the relevant full matrix.

---

# 14. Reference-source recording

Every external or independent reference vector used by R0.13 must record:

```text
source
version / edition where applicable
formula or table identifier where practical
input value
reference output
reference precision
whether the value is normative or derived
```

Do not copy a displayed decimal with fewer significant digits than needed and
then infer a tighter error bound than the reference itself supports.

Where a standard gives a formula rather than a high-precision decimal result,
R0.13 may derive a higher-precision reference independently, but must record
that distinction.

---

# 15. Measurement rules

Numerical characterization must distinguish:

```text
semantic pass/fail criterion
```

from:

```text
observed error statistics
```

Record observations such as:

```text
maximum absolute error
maximum relative error
maximum ULP distance
input that produced the maximum
reference magnitude
compiler
build mode
scalar type
runtime or CTFE
```

but do not automatically set the acceptance threshold equal to the measured
maximum.

A tolerance must include a reasoned margin derived from numerical semantics,
reference quality and observed implementation behavior.

---

# 16. Candidate production helpers

R0.13 must explicitly decide whether any comparison helper belongs in
production `color-d`.

Possible outcomes include:

## Outcome A — test-only comparison infrastructure

Production operations expose no generic approximate comparator.

Tests use internal helpers appropriate to each property.

## Outcome B — low-level generic numerical helper

A narrowly specified helper may be justified if it has semantics independent of
color policy and consumers.

## Outcome C — explicit policy object for selected APIs

An explicit numerical-policy type may be justified only where tolerance is part
of a real runtime question, such as a caller-requested numerical-boundary test.

R0.13 must not promote a generic helper merely because many tests need similar
syntax.

# 18. Explicit non-goals

R0.13 does not establish:

- application color-difference acceptance thresholds;
- UI contrast policy;
- design-token acceptance policy;
- a universal gamut-boundary fuzz factor;
- one epsilon for all color spaces;
- one epsilon for both float and double;
- compiler-independent bit patterns;
- arbitrary precision guarantees;
- exhaustive formal floating-point proofs;
- public API names unrelated to numerical comparison;
- final v1.0 compatibility guarantees.

---

# 19. Promotion rule

Research-local tolerances are evidence, not API.

A numerical threshold may be promoted only when its purpose is explicit and its
derivation is supported by:

```text
the mathematical property
the reference source
the scalar type
the tested implementation behavior
the required portability contract
```

A test passing is not sufficient justification.

---

# 20. Success criteria

R0.13 succeeds if it can answer:

1. Which color-d properties require exact equality?
2. Which comparisons require external or independent references?
3. Which operation classes require approximate numerical comparison?
4. Which approximate comparisons should use absolute, relative, combined or
   ULP-oriented criteria?
5. How do `float` and `double` differ?
6. How should NaN, infinity and signed zero be handled per comparison class?
7. How should strict boundary classification differ from numerical proximity?
8. What runtime/CTFE agreement is required?
9. What compiler-cross agreement is required?
10. Which comparison helpers remain test infrastructure?
11. Does any tolerance-bearing helper belong in production API?
12. Can the resulting policy be promoted into R1 production tests without a
    universal epsilon?

No public API is frozen by this contract.
