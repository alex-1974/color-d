# v0.1.0 feature freeze

**Status:** COMPLETE — ENDED WITH v0.1.0  
**Release target:** `v0.1.0`  
**Tracking:** #14

## Decision

The accepted `color-d` feature scope for v0.1.0 is frozen.

The freeze applies to **feature scope**, not to all code changes. R1-R3 define
the accepted production functionality. R4 real-consumer validation is complete
and did not demonstrate a need to change the public API or reopen feature
scope.

Release hardening must not become a second feature-development phase.

## Frozen scope

The v0.1 scope is the production functionality already documented and tested
for:

- typed encoded and linear-light sRGB;
- XYZ D65;
- Oklab and OKLCH;
- `float` and `double` scalar families;
- explicit color-space conversions;
- straight and premultiplied alpha plus linear-light source-over compositing;
- same-space and OKLCH interpolation with explicit hue-path policy;
- strict gamut testing and explicit clipping;
- explicit Local MINDE and Ray Trace sRGB gamut mapping;
- WCAG-2 relative luminance and contrast;
- Oklab `deltaEOK`;
- low-level OKLCH component and tone-family primitives;
- the accepted root and direct-module import surface.

The maintained semantics are defined by production source/Ddoc, tests, user
documentation, accepted ADRs, and release metadata. Historical research is
evidence, not an additional production contract.

## Allowed during the freeze

The following remain valid v0.1 work:

- reproduced defect fixes with regression evidence where practical;
- evidence-backed corrections to an existing v0.1 contract;
- tests, compile probes, canaries, and independent validation;
- README, Ddoc, tutorials, CHANGELOG, release notes, and support statements;
- CI, packaging, documentation publication, and release engineering;
- security or confirmed compiler/runtime adaptations;
- measured performance fixes for accepted v0.1 operations;
- repository/research separation needed to keep the release and production
  repository lean.

Pre-1.0 breaking corrections remain possible only when concrete evidence shows
the accepted contract is ambiguous, wrong, or materially impractical.

## Not allowed during the freeze

Do not add new feature scope merely because it is useful or convenient.

Examples include:

- new color spaces;
- new packed/storage color families;
- new palette/theme abstractions;
- parsing or serialization families;
- accessibility/tooling feature families;
- generic convenience APIs that duplicate explicit operations;
- a default gamut mapper;
- policy-heavy application abstractions;
- speculative aliases or shortcuts;
- broad refactors without a correctness/release/consumer reason;
- speculative compiler-specific optimization.

Deferred candidates such as `SRgb8` / `SRgba8`, HSL / HSV, Display-P3,
Rec.2020, CIELAB / LCh, CIEDE2000, Okhsl / Okhsv, CSS
parsing/serialization, palette systems, color-vision-deficiency tooling, HDR,
and ICC / CMYK remain deferred.

## Reopening the freeze

The freeze may be reopened only through an explicit release-scope decision that
records:

1. concrete blocking evidence;
2. why the existing accepted surface cannot satisfy the need;
3. why deferral beyond v0.1 is unacceptable;
4. the exact additional scope;
5. required tests, documentation, and performance evidence;
6. impact on release timing and public API;
7. whether renewed consumer validation is required.

After the narrowly approved addition is complete, the freeze resumes.

## End of freeze

The feature freeze ended with publication of v0.1.0 on 2026-09-29.

This document remains as the historical policy that governed the first-release
hardening period. Post-v0.1 work follows the normal `develop` workflow and must
not retroactively change the v0.1.0 contract.
