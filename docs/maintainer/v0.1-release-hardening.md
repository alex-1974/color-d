# v0.1 release-hardening entry audit

Entered: 2026-09-28  
Release metadata finalized: 2026-09-29

This is a compact production-repository summary of the state entering the
v0.1.0 release-hardening phase. Raw research and experiment evidence remains
outside this summary.

## Scope

The accepted R1-R3 feature scope remains frozen. R4 real-consumer validation is
complete. Release hardening may change tests, documentation, CI, packaging,
release engineering, confirmed defects, and evidence-driven toolchain or
performance adaptations. It does not add feature families or speculative
convenience API.

## Real consumers

Two independent workspace consumers exercised the production surface:

- `imagery-d` issue #18 / color-d #4: typed encoded-sRGB to linear-sRGB
  transfer inside real raster-region processing, covering planar/interleaved
  layout equivalence, ROI partition equivalence, caller-owned output,
  `@safe nothrow @nogc`, CTFE of the scalar primitive, and DMD/LDC execution.
- Dunia PR #2 / color-d #13: selection/accent theme construction using the
  public root import, OKLCH state/tone derivation, explicit Ray Trace gamut
  mapping, encoded/linear prepared values, WCAG contrast, `deltaEOK`, CTFE
  built-ins, runtime user-accent construction, and background-dependent
  selection among prepared candidates.

Neither consumer demonstrated actionable color-d API friction. Application,
image, renderer, OSM, theme-role, and background-selection policy remained
outside color-d.

## Public surface audit

The production source tree contains exactly:

- the root entry module `color/package.d`;
- eleven supported public modules:
  `rgb`, `xyz`, `oklab`, `oklch`, `alpha`, `composite`,
  `interpolate`, `gamut`, `wcag`, `difference`, and `tone`.

The root module re-exports exactly those eleven modules.

No additional implementation module is technically importable from `source/`.
Internal module helpers are `private`; the one cross-module implementation
hook `toLinearSRgbDirect` is `package(color)`. No accidental unsupported
module family was found.

The release workflow separately compiles:

- the curated root import;
- all documented direct public module imports;
- negative compile contracts for intentionally absent/invalid API forms.

## Support statement

The intended v0.1 tested matrix remains:

- DMD 2.113.0, Ubuntu 24.04 x86-64;
- LDC 1.43.0, Ubuntu 24.04 x86-64.

No older minimum frontend is promised. LDC remains the release-performance
reference compiler.

## Package and publication state

Release-commit state:

- v0.1.0 release metadata is finalized on the dedicated release branch;
- promotion to `main` is permitted only through the protected DMD/LDC Release Gate;
- the exact promoted `main` commit must be tagged immediately with annotated `v0.1.0`;
- tag-driven publication then performs final qualification, GitHub Release asset
  publication, and stable/versioned Pages reconstruction.

Already implemented:

- consumer archive boundary via `.gitattributes export-ignore`;
- clean external DUB consumer checks;
- DMD/LDC promotion-to-main release gate;
- tag-driven publication workflow;
- deterministic consumer and DDox release archives plus checksums;
- stable/versioned/development Pages reconstruction;
- non-destructive publication dry-run coverage.

At release-branch finalization, the remaining ordered actions are:

1. protected release PR to `main`;
2. exact release-commit selection by that merge;
3. deliberate annotated `v0.1.0` tag creation;
4. tag-driven final qualification and GitHub Release/Pages publication;
5. post-publication DUB registry resolution and clean released-consumer check.

DUB registry publication/resolution remains an external post-tag verification;
release metadata must not claim registry availability before that succeeds.
