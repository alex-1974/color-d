# v0.2.0 real-consumer validation

Status: **qualification fixture implemented; CI result pending**

Issue: #155

## Purpose

Before the v0.2.0 release is stabilized, the new storage and hexadecimal
interop surface must be exercised from a consumer package rather than only
through provider-side unittests.

The accepted boundary remains:

```text
external/config/byte storage
        -> SRgb8 / SRgba8
        -> explicit computational sRGB
        -> explicit color mathematics

consumer policy
        -> remains outside color-d
```

## Consumer fixture

`tests/consumer/v0_2_storage_interop` is a separate DUB executable package.
It imports only the public root module:

```d
import color;
```

It deliberately does not import implementation modules or package-private
helpers.

The fixture models two concrete consumers.

### Editor/configuration path

```text
#RRGGBBAA configuration value
        -> tryParseSRgba8Hex
        -> SRgba8
        -> toAlphaSRgb!float
        -> explicit RGB toLinear
        -> consumer-owned editor token
```

The same path is exercised during CTFE for a fixed built-in selection color and
at runtime for configuration input.

The consumer owns the semantic editor token. color-d does not learn roles such
as selection, hover, warning, map background, or theme policy.

### Imagery/renderer path

```text
raw RGBA bytes
        -> SRgba8
        -> Alpha!SRgbf
        -> checked tryToSRgba8
        -> raw RGBA bytes
```

The fixture requires exact byte round-trip behavior and explicitly checks
straight-alpha hidden RGB at alpha zero.

## Required behavior

The consumer mechanically verifies:

- API reachability through `import color;`;
- CTFE parsing and conversion for fixed configuration data;
- runtime parsing of exact full-byte hexadecimal RGBA;
- deterministic lowercase hexadecimal serialization;
- storage -> computational -> storage byte round-trip;
- straight alpha and hidden RGB preservation;
- explicit linear-light boundary conversion;
- rejection of unsupported shorthand without destination modification;
- checked failure for out-of-range computational values without destination
  modification;
- consumer helper compatibility with `@safe pure nothrow @nogc`;
- no provider-side theme, renderer, or clipping policy is required.

## Existing real consumers

The release consumer gate continues to run the already accepted pinned
consumers in addition to the v0.2 fixture:

- imagery-d sRGB transfer consumer;
- Dunia theme/selection consumer;
- raster-d at the pinned dependency required by imagery-d.

This ensures the new storage surface does not invalidate the previously
accepted library boundary.

## CI integration

`.github/scripts/run-real-consumer-gates.sh` runs:

1. the v0.2 external storage/interop fixture;
2. the pinned imagery-d consumer;
3. the pinned Dunia consumer.

`.github/workflows/release-consumer-canary.yml` runs the gate with:

- DMD 2.113.0 / debug;
- LDC 1.43.0 / release.

The canary is triggered when the fixture, gate script, release consumer
workflow, or relevant storage/RGB/alpha public source changes.

## Promotion rule

If the consumer fixture exposes API friction, the provider API is corrected
before release stabilization. Application-specific adapters are not added to
hide a provider-side defect.

Issue #155 closes only after both canary jobs pass and the observed consumer
boundary requires no color-d API correction.
